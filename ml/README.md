# ml/ — графовая нейросеть для прогноза загруженности дорожной сети

Часть дипломного проекта «Проектирование архитектуры интеллектуальной системы
моделирования и оптимизации городской транспортной сети».

Задача модуля: по описанию дорожной сети района и списку изменений,
которые пользователь вносит на карте (закрыть улицу, изменить число полос
или разрешённую скорость, поставить/убрать светофор), **за миллисекунды**
предсказать для каждого участка дороги:

| величина | смысл | единицы |
|---|---|---|
| `occupancy` | занятость — доля длины участка, занятая машинами | 0..1 |
| `mean_speed` | средняя скорость движения | м/с |
| `travel_time` | время проезда участка | с |

Модель обучается на результатах микросимуляции SUMO (часть `sim/`) и в
рабочем режиме приложения заменяет её: SUMO считает один вариант сети
десятки секунд, а нейросеть — миллисекунды (см. «Результаты»).

## Что сделано

1. **Загрузчик датасета** `sim/data/dataset/*.parquet` (`dataset.py`), терпимый к
   деталям формата SUMO (синонимы колонок edgeData, occupancy в процентах,
   интервалы агрегации, внутренние рёбра перекрёстков). Пока датасета от
   `sim/` нет — **синтетический датасет того же формата** (`synthetic.py`),
   который строит упрощённая макроскопическая транспортная модель
   (`macro.py`: функция задержки BPR + равновесное распределение потоков).
2. **Модель GNN** (`model.py`): рёбра дорог — узлы *line graph*;
   направленный GraphSAGE (и для сравнения GATv2) с остаточными связями,
   предсказывающий изменение метрик относительно базового состояния.
3. **Бейзлайны** (`baselines.py`): «прогноз = без изменений», линейная
   (гребневая) регрессия, градиентный бустинг.
4. **Обучение и оценка** (`train.py`): MAE / RMSE / R² по каждой метрике,
   R² *изменения*, ошибки рядом с изменениями и по типам изменений, кривые
   обучения, сравнение с бейзлайнами, карта тестового сценария, замер времени
   инференса (`benchmark.py`) — всё в `ml/reports/`.
5. **`ml/predict.py`** по контракту + сохранённые веса в `ml/weights/`.
6. **Заглушка сети** `network.json` (`stub_network.py`), пока её не выдала
   `sim/`: из OSM-карты района через `netconvert` или решётка 4×4 через
   `netgenerate`.
7. **Тесты** (`ml/tests/`, pytest): семантика изменений, признаки,
   макромодель, загрузчик (включая формат «как у SUMO»), сквозной тест
   «обучение → веса → predict по контракту».

## Быстрый старт

Все команды — из корня репозитория, Python 3.11.

```bash
python3.11 -m venv .venv && source .venv/bin/activate
# PyTorch для CPU (~200 МБ вместо ~3 ГБ сборки с CUDA)
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r ml/requirements.txt

# Прогноз готовыми весами (веса и сеть, на которой они обучены, лежат в ml/weights/)
python -m ml.predict --changes '[{"type": "close", "target_id": "-188843654#8", "value": null}]'

# Полный цикл: (заглушка сети) → (синтетический датасет) → обучение → отчёты (~1,5 ч на 4 ядрах CPU)
python -m ml.train
# Быстрая проверка конвейера (≈1 мин)
python -m ml.train --quick --weights-dir /tmp/w --reports-dir /tmp/r

# Отдельные шаги
python -m ml.stub_network            # заглушка network.json (ml/data/stub/…)
python -m ml.synthetic --n 3000      # синтетический датасет (ml/data/synthetic/, ~3 мин)
python -m ml.benchmark               # замер времени инференса (+ прогон SUMO для сравнения)
python -m ml.report                  # перерисовать графики без переобучения

# Тесты (~1 мин)
python -m pytest ml/tests -q
```

Датасет SUMO от `sim/` уже есть (`sim/data/network.json` + `sim/data/dataset/*.parquet`),
поэтому `python -m ml.train` по умолчанию учится на нём (флаг `--source sim|synthetic`
выбирает источник явно). Веса в `ml/weights/` обучены на пилотном датасете sim/
(300 сценариев) командой

```bash
python -m ml.train --source sim --models sage --max-minutes 12 --final-minutes 15 \
                   --reports-dir ml/reports/sim_pilot
```

Отчёт — [`reports/sim_pilot/metrics.md`](reports/sim_pilot/metrics.md); отчёты обучения на
синтетике (разделы «Результаты» ниже) остались в `reports/`. Каталог с данными симуляции
можно переопределить переменной окружения `IIGONI_SIM_DATA`.

## Интерфейс для backend (контракт)

```python
from ml.predict import predict, model_info

forecast = predict(network, changes)
# network — dict в формате sim/data/network.json
# changes — список изменений:
#   {"type": "lanes",         "target_id": <edge_id>, "value": 3}       # новое число полос (>= 1)
#   {"type": "speed",         "target_id": <edge_id>, "value": 11.11}   # новая скорость, м/с
#   {"type": "close",         "target_id": <edge_id>, "value": None}    # перекрыть участок
#   {"type": "open",          "target_id": <edge_id>, "value": None}    # открыть участок
#   {"type": "traffic_light", "target_id": <node_id>, "value": True}    # True — поставить, False — убрать,
#                                                                       # None — убрать (как в sim/)
# forecast — {edge_id: {"occupancy": 0.123, "mean_speed": 9.87, "travel_time": 14.2, "closed": False}}
```

Детали поведения:

* Прогноз возвращается **для каждого ребра** сети. Для закрытого ребра:
  `{"occupancy": 0.0, "mean_speed": 0.0, "travel_time": None, "closed": True}`
  (`None` → `null` в JSON: проезд невозможен). Поле `closed` — дополнение к
  контракту, у открытых рёбер оно `False`.
* Изменения применяются **последовательно**: `close X`, затем `open X` —
  ребро открыто. Скорость больше 50 считается заданной в км/ч и переводится
  в м/с (с предупреждением в лог). Для `traffic_light` понимаются также строки
  `"add"/"on"/"remove"/"off"` и режимы `"fixed"/"actuated"/"rl"` (= светофор есть).
* Некорректное изменение (неизвестный тип, несуществующий `target_id`,
  `lanes < 1`, нечисловое значение) → `ValueError` с понятным текстом —
  удобно отдавать как HTTP 400.
* `predict(network, [])` в точности равен базовому состоянию сети (если
  изменений относительно эталона нет, модель не вызывается), поэтому для
  карты «до» можно вызывать ту же функцию.
* Если backend хранит сеть **уже с внесёнными правками**, их можно не
  дублировать в `changes`: переданная сеть сравнивается с эталонной (той, на
  которой обучена модель), и разница учитывается как изменения.
* Модель загружается один раз на процесс (ленивый кэш), подготовленный
  line graph кэшируется по структуре сети; вызов потокобезопасен.
* `model_info()` — архитектура, дата обучения, источник данных и метрики
  на тесте (для отображения в интерфейсе).
* Для сети, рёбер которой модель не видела, прогноз тоже работает (GNN
  индуктивна), но базовое состояние таких рёбер неизвестно и считается
  «свободным потоком» — для точного прогноза модель нужно переобучить на
  датасете этой сети (`python -m ml.train`).

## Данные: формат датасета и заглушки

### Формат, который ожидает загрузчик

`sim/data/network.json` — по контракту. Плюс parquet-файлы датасета: sim/ пишет их в
`sim/data/dataset/` — `edges.parquet` (метрики рёбер) и `scenarios.parquet` (изменения);
`nodes.parquet` в обучение не идёт, а `seed_noise.parquet` (базовая сеть при 8 зёрнах
SUMO) используется для оценки шумового пола: в самом датасете один базовый прогон, потому
что все сценарии считаются с одним зерном (метод общих случайных чисел). Загрузчик
принимает и файлы прямо в `sim/data/`. Общий вид таблиц:

**`scenarios.parquet`** — по строке на сценарий (прогон SUMO):

| колонка | тип | описание |
|---|---|---|
| `scenario_id` | int64 | идентификатор прогона |
| `changes` | string | JSON-список изменений по контракту; `"[]"` — базовый прогон |
| `seed` | int64 | (необязательно) seed прогона |

**`edge_metrics.parquet`** — по строке на (сценарий, ребро):

| колонка | тип | описание |
|---|---|---|
| `scenario_id` | int64 | |
| `edge_id` | string | id ребра из network.json |
| `occupancy` | float | доля 0..1 (проценты из edgeData SUMO распознаются автоматически) |
| `mean_speed` | float | м/с |
| `travel_time` | float | с |

Загрузчик также принимает: одну общую таблицу с колонкой `changes`;
синонимы колонок edgeData SUMO (`id`→`edge_id`, `speed`→`mean_speed`,
`traveltime`→`travel_time`, `scenario`→`scenario_id`); несколько строк на
пару (сценарий, ребро) — например интервалы агрегации — усредняются; рёбра,
которых нет в network.json (внутренние `:…` рёбра перекрёстков), отбрасываются.
Закрытые в сценарии рёбра могут отсутствовать. **Базовое состояние** —
среднее по сценариям с `changes = []` (их желательно несколько с разными
seed — это заодно оценка стохастического шума SUMO).

### Заглушка сети (`stub_network.py`)

Пока нет `sim/data/network.json`, сеть строится тем же инструментом (SUMO)
и в том же формате, результат кладётся в `ml/data/stub/` (в чужие папки
модуль не пишет). Порядок выбора источника:

1. `sim/data/network.json` (настоящий результат `sim/`);
2. `sim/data/map.osm` → `netconvert`;
3. **`map.osm` в корне репозитория** — та же карта района, загруженная автором
   проекта (центр Петропавловска, ≈ 1,9 × 3,2 км). Сейчас используется именно
   она: 355 перекрёстков, 907 участков дорог, 33 светофора;
4. решётка 4×4 через `netgenerate` (магистрали — столбец B и строка 2,
   2 полосы, 60 км/ч, светофоры на их перекрёстках; без SUMO — та же решётка
   на Python). Используется в тестах.

Опции `netconvert`: только дороги для легковых (`--keep-edges.by-vclass passenger`),
объединение сложных перекрёстков (`--junctions.join`), светофоры из OSM
(`--tls.guess-signals`, `--tls.join`), без разворотов кроме тупиков.

### Синтетический датасет (`synthetic.py`, `macro.py`)

Нужен, чтобы отладить и честно сравнить модели до появления данных SUMO.
Требование к генератору — воспроизводить **сетевые эффекты**: закрытие
улицы перераспределяет поток на соседние, снижение пропускной способности
вызывает затор и объезд. Поэтому используется классическая схема
макромоделирования:

* спрос — гравитационная матрица корреспонденций между 84 зонами (24 граничных
  узла района — транзит, 60 внутренних — местные поездки) + фоновый местный
  трафик на каждой улице;
* время проезда — функция BPR `t = t0·(1 + 0.15·(v/c)^4)`, где `t0` включает
  задержку на перекрёстке (светофор — по Вебстеру при доле зелёного 0,45;
  второстепенное направление — коэффициент 0,55 к пропускной способности);
* потоки — приближённое равновесие по Вардропу методом последовательных
  усреднений (MSA, 30 итераций);
* выход: `travel_time = t`, `mean_speed = длина / t`, `occupancy` — из числа
  машин на участке по формуле Литтла;
* стохастичность SUMO имитируется случайным возмущением матрицы спроса в
  каждом сценарии (логнормальный шум σ = 0,3 на корреспонденцию);
* спрос калибруется так, чтобы 95-й перцентиль загрузки v/c в базе был ≈ 1
  (умеренно загруженная сеть).

Сценарии: 10 базовых прогонов + 3000 случайных наборов из 1–4 изменений
(закрытие 35 %, полосы 30 %, скорость 20 %, светофор 15 %; «пользователь»
чаще меняет крупные улицы, перекрытие с вероятностью 1/2 закрывает оба
направления). Генерация — ≈ 3 мин на 4 ядрах.

## Модель

### Граф: участки дорог — узлы (line graph)

Прогноз нужен по рёбрам дорожной сети, а GraphSAGE/GAT предсказывают
значения для узлов графа. Поэтому сеть переводится в **line graph**: каждый
участок дороги становится узлом, а направленная связь «a → b» проводится,
если с участка `a` можно выехать на участок `b` (`a.to == b.from`), кроме
разворотов (оставлены только в тупиках). Для сети района: 907 узлов и
2015 связей line graph.

### Признаки участка (22)

| группа | признаки |
|---|---|
| структура | log(длины), приоритет, число въездов в начальный узел, выездов из конечного, «въезд/выезд района» |
| состояние после изменений | полосы, разрешённая скорость, log(время свободного проезда), светофор в начале/конце, закрыт |
| разница с базой | Δполос, Δскорости, светофор поставлен/снят (в начале/конце), «ребро изменено» |
| базовое состояние | занятость, скорость/лимит, log(время/время свободного проезда), log интенсивности потока (по формуле Литтла из занятости и времени) в прогоне без изменений, «база известна» |

Сами изменения в модель не подаются списком: они применяются к копии сети,
и модель видит итоговое состояние и его разницу с базой. Поэтому модель не
зависит от порядка и числа действий пользователя, а `close`+`open` корректно
сводятся к «ничего не изменилось».

### Целевые величины (нормированные)

* `occupancy` — как есть (0..1);
* `mean_speed / лимит` — доля от разрешённой скорости;
* `log(travel_time / (длина / лимит))` — логарифм индекса задержки
  (убирает тяжёлый хвост времени проезда на заторных участках).

Модель предсказывает **изменение Δ** этих величин относительно базового
состояния (итог = база + Δ), стандартизованное по обучающей выборке.
Закрытые рёбра исключены из функции потерь: их выход задаётся правилом.

### Архитектура

```
x (22 признака) → MLP-кодировщик (64) → 6 × DirectionalBlock(d) → голова [h ‖ x] → Δ (3)
                                         d = 1, 1, 2, 2, 4, 4

DirectionalBlock(d):  m = W_self·h + SAGE_вверх^d(h) + SAGE_вниз^d(h) + W_g·mean_по_графу(h)
                      h ← h + Dropout(GELU(LayerNorm(m)))
```

`SAGE_вверх^d` усредняет состояния участков, с которых до данного можно
доехать ровно за `d` переходов, `SAGE_вниз^d` — участков, куда можно доехать
за `d` переходов.

* **Раздельные веса для потоков «сверху» и «снизу»**: затор распространяется
  против движения, а перераспределённый поток — по движению; один общий
  агрегатор их бы смешал.
* **Расширенные (dilated) связи.** Анализ датасета показал, что эффект
  изменения дальнобойный: из рёбер с заметным изменением занятости
  (|Δ| > 3 п.п.) в пределах 6 переходов от правки лежит лишь 71 %, в пределах
  10 — 89 %. Обычная 6-слойная GNN «видит» только 6 переходов, а 12+ слоёв
  медленны и склонны к пересглаживанию. Поэтому слои по очереди берут
  соседей через 1, 1, 2, 2, 4, 4 перехода — рецептивное поле 14 переходов при
  6 слоях и почти той же скорости. Связи «ровно через d переходов» считаются
  разреженными степенями матрицы смежности line graph (для сети района:
  2015 / 4497 / 15989 связей для d = 1 / 2 / 4).
* **Остаточные связи + LayerNorm** — сохраняют локальную информацию при
  смешивании дальних сообщений.
* **Глобальное среднее по графу** («виртуальный узел») — каждый участок
  знает о сценарии в целом (сколько и чего изменено).
* **Нулевая инициализация последнего слоя** — в начале обучения модель
  совпадает с бейзлайном «без изменений» и учится только эффекту правок.
* **«До» = база.** Если после применения изменений сеть совпадает с
  эталонной, `predict` возвращает базовое состояние без вызова модели
  (сценариев без изменений нет в обучении, выход модели на них —
  экстраполяция). Дополнительно проверяется «поправка нуля» — вычитание
  из Δ выхода модели для сети без изменений; она включается, только если
  уменьшает ошибку на валидации.
* **Скорость на CPU.** Усреднение по соседям в `SAGEConv` (PyG) выполняется
  через разреженную матрицу смежности (`adj_t`, CSR) — это то же самое
  вычисление, но в ~7 раз быстрее, чем поэлементная рассылка сообщений по
  `edge_index`.

**Обучение в два этапа.**

1. **Абляция** — варианты обучаются с равным бюджетом времени (15 мин CPU
   на вариант), чтобы честно сравнить архитектуры:

| вариант | свёртка | связи по слоям |
|---|---|---|
| `sage` (основной) | GraphSAGE (среднее) | 1, 1, 2, 2, 4, 4 перехода |
| `sage_local` | GraphSAGE (среднее) | 1 переход во всех слоях |
| `gat_local` | GATv2 (внимание) | 1 переход во всех слоях |

GATv2 на расширенных связях не обучается за разумное время на CPU
(внимание считается для каждой из ~16 тыс. связей «через 4 перехода»,
≈ 0,6 с на слой для батча), поэтому сравнивается в локальном варианте:
`sage_local` против `gat_local` — эффект внимания, `sage` против
`sage_local` — эффект расширенных связей.

2. **Итоговая модель** — лучший по валидации вариант дообучается ещё 30 мин
   с косинусным затуханием шага обучения (от 10⁻³ до 10⁻⁵). Именно она
   сохраняется в `ml/weights/` и используется в `predict.py`.

Общие настройки: AdamW (lr 2·10⁻³, weight decay 10⁻⁵), MSE по
стандартизованной Δ, батч 16 сценариев, ReduceLROnPlateau и ранняя
остановка (15 эпох) на этапе абляции; лучшие веса выбираются по валидации.
Веса вариантов абляции сохраняются в `ml/data/ablation/`, флаг
`--reuse-ablation` позволяет не переобучать их при повторном запуске.

## Бейзлайны и методика сравнения

| модель | что делает |
|---|---|
| Без изменений | Δ = 0: после правок всё как в базе. Нижняя граница |
| Линейная регрессия | Ridge на табличных признаках |
| Градиентный бустинг | `HistGradientBoostingRegressor` (scikit-learn), по модели на метрику |

Все модели предсказывают одну и ту же величину (Δ нормированных метрик) на
одних и тех же признаках. Табличные модели граф не видят, поэтому им
дополнительно даётся **инженерный контекст** сценария: число изменений
каждого типа и расстояние (в переходах) до ближайшего изменения вверх и вниз
по потоку. Это делает сравнение строже — бейзлайнам «сказано», где правки.

* Разбиение 70/15/15 — **по сценариям**, а не по строкам (иначе одно и то же
  изменение попало бы и в обучение, и в тест).
* Метрики считаются в физических единицах по всем открытым рёбрам тестовых
  сценариев. Так как правки затрагивают лишь часть сети, а остальная сеть
  «шумит» (стохастичность прогонов), дополнительно считаются:
  * **R² изменения (Δ)** — R² между прогнозом и фактом *изменения* относительно
    базы: доля объяснённого эффекта правок (у «без изменений» ≈ 0);
  * метрики **рядом с изменениями** — рёбра не дальше 3 переходов от правок;
  * ошибки **по типу изменения** (закрытие, полосы, скорость, светофор, комбинация).

## Результаты

### Пилотный датасет SUMO (sim/) — веса в `ml/weights/`

Сеть района из sim/ (836 участков, 1887 связей line graph), 301 сценарий: обучение 210 /
валидация 45 / тест 45. Обучен основной вариант (GraphSAGE + расширенные связи: 5,8 мин +
дообучение 15 мин), абляция на этих данных не повторялась. Полный отчёт —
[`reports/sim_pilot/metrics.md`](reports/sim_pilot/metrics.md).

| модель | MAE занятости | R² Δ занятости | R² Δ занятости рядом | MAE скорости, м/с | R² Δ скорости | MAE времени, с | R² Δ времени |
|---|---:|---:|---:|---:|---:|---:|---:|
| Без изменений | 0.0029 | 0.00 | 0.00 | 0.333 | 0.00 | 1.58 | 0.00 |
| Линейная регрессия | 0.0032 | 0.01 | 0.03 | 0.351 | 0.09 | 1.68 | −0.08 |
| Градиентный бустинг | 0.0026 | 0.25 | 0.26 | 0.280 | 0.35 | 1.41 | 0.13 |
| **GNN (итоговая)** | **0.0025** | **0.35** | **0.44** | **0.276** | **0.38** | **1.37** | **0.16** |

* Шумовой пол — разброс базового прогона по 8 зёрнам SUMO (`sim/data/dataset/seed_noise.parquet`):
  занятость 0.0019, скорость 0.32 м/с, время 1.26 с. Сценарии датасета считаются с тем же зерном,
  что и база, поэтому для разницы «сценарий − база» шум меньше этой оценки.
* GNN лучше бейзлайнов по всем метрикам, но объясняет лишь треть эффекта изменений (на синтетике
  с 2100 сценариями обучения — 72 %): 210 сценариев мало, ошибка на обучении продолжает падать, а на
  валидации — нет. Нужен полный датасет (см. «Что осталось сделать» в корневом README.md).
* `predict()` на сети района — 7,7 мс (медиана).

### Синтетический датасет (макромодель ml/)

Сеть района (907 участков), синтетический датасет — 3010 сценариев, из них
тестовых 450, которые модель не видела. Полные таблицы — в
[`reports/metrics.md`](reports/metrics.md), графики — в `reports/`.

#### Сравнение с бейзлайнами (тест)

| модель | MAE занятости | R² Δ занятости | MAE скорости, м/с | R² Δ скорости | MAE времени, с | R² Δ времени |
|---|---:|---:|---:|---:|---:|---:|
| Без изменений | 0.0062 | 0.00 | 0.043 | 0.00 | 0.081 | 0.00 |
| Линейная регрессия | 0.0062 | 0.04 | 0.040 | 0.71 | 0.083 | −0.16 |
| Градиентный бустинг | 0.0061 | 0.25 | 0.034 | 0.84 | 0.067 | 0.68 |
| **GNN (итоговая)** | **0.0049** | **0.72** | **0.029** | **0.93** | **0.052** | **0.88** |

Как читать:

* Обычный R² у всех моделей ≈ 0,99: большая часть сети от правок почти не
  меняется, и даже «без изменений» хорошо воспроизводит базовую карту.
  Поэтому главная метрика — **R² изменения (Δ)**: доля объяснённого эффекта
  правок. GNN объясняет 72 % изменения занятости, бустинг — 25 %.
* MAE по всей сети ограничена снизу **шумовым полом** — стохастичностью
  прогонов (MAE занятости между базовыми прогонами с разными seed — 0,0029).
  GNN сократила разрыв между бейзлайном (0,0062) и этим пределом примерно
  вдвое.
* **Рядом с изменениями** (≤ 3 перехода) R² Δ занятости у GNN — 0,85, у
  бустинга — 0,37. Сильнее всего GNN выигрывает на **закрытиях** и
  **светофорах**, то есть там, где эффект сетевой — перераспределение потока.
  MAE занятости около закрытий: 1,1 п.п. у GNN против 2,2 у бустинга и 2,4
  у «без изменений». Изменения скорости и числа полос в основном
  локальные, с ними неплохо справляется и бустинг.
* На карте тестового сценария (`reports/example_scenario.png`) видно: GNN
  воспроизводит и объезды (красные), и разгрузившиеся улицы (синие), а
  бустинг — только эффект на самом изменённом участке.

#### Абляция (равный бюджет 15 мин CPU)

| вариант | эпох | val loss | R² Δ занятости (тест) | R² Δ времени (тест) |
|---|---:|---:|---:|---:|
| GraphSAGE + расширенные связи | 37 | 0.184 | 0.628 | 0.860 |
| GraphSAGE, только соседи | 45 | 0.186 | 0.622 | 0.854 |
| GATv2, только соседи | 18 | 0.225 | 0.529 | 0.764 |
| **итоговая: лучший вариант + 30 мин дообучения** | 103 | **0.143** | **0.719** | **0.882** |

* GATv2 при равном времени заметно хуже: эпоха с вниманием в 2,5 раза
  дороже на CPU (49 с против 19 с), и за то же время модель проходит
  в 2,5 раза меньше эпох. Выбор GraphSAGE подтверждён экспериментом.
* Расширенные связи дают меньшую ошибку на эпоху: 0,184 после 37 эпох
  против 0,186 после 45. Но эпоха с ними дороже (26 с против 19 с), поэтому
  при равном времени разница в пределах шума. Для итоговой модели выбран
  вариант с меньшей ошибкой на валидации — с расширенными связями.
* Дообучение с косинусным затуханием шага дало наибольший прирост: val loss
  0,184 → 0,143. Кривые обучения (`reports/training_curves.png`) показывают,
  что модель ещё не вышла на плато: на данных SUMO стоит дать ей больше
  времени.

#### Время инференса (CPU, 4 ядра)

| | время |
|---|---:|
| `predict()` на сети района (907 рёбер), медиана / 95-й перцентиль | **8,3 мс** / 9,6 мс |
| только прямой проход GNN | 4,1 мс |
| холодный старт (загрузка весов + первый вызов) | 39 мс |
| макромодель-генератор, 1 сценарий | 231 мс |
| SUMO, 1 ч модельного времени на той же сети (3600 ТС) | 5,2 с |

GNN примерно в 600 раз быстрее одного прогона SUMO. Время растёт почти
линейно с размером сети: 64 мс на решётке из 9408 рёбер
(`reports/inference_time.png`). Это позволяет пересчитывать тепловую карту
сразу после каждого действия пользователя.

## Принятые решения и их обоснование

| решение | почему |
|---|---|
| Line graph (участки — узлы) | метрики нужны по рёбрам; стандартные GNN работают с узлами; связи line graph — реальные маневры |
| GraphSAGE как основная свёртка, GATv2 для сравнения | SAGE индуктивна (работает на сетях любого размера), а усреднение реализуется разреженным умножением матриц — быстро на CPU; выбор подтверждается абляцией с равным бюджетом времени |
| Направленные сообщения (вверх/вниз по потоку) | затор и перераспределение потока распространяются в разные стороны |
| Расширенные связи 1, 1, 2, 2, 4, 4 | эффекты правок доходят до 8–12 переходов; так рецептивное поле 14 переходов без 14 слоёв |
| Признак «интенсивность потока» по формуле Литтла | при закрытии важно, сколько машин перераспределится; выводится из занятости и времени проезда — новых полей от sim/ не нужно |
| Прогноз Δ относительно базы + нулевая инициализация | модель не хуже «без изменений» с первой эпохи, ёмкость тратится на эффект правок |
| Нормировка целей (доля от лимита, log задержки) | сопоставимость улиц разных категорий, нет тяжёлого хвоста у времени проезда |
| Изменения → итоговое состояние + разница с базой | порядок и число действий не важны, `open` после `close` корректен |
| Закрытые рёбра — по правилу, вне функции потерь | у закрытого участка нет метрик (в SUMO его нет в edgeData) |
| Эталонная сеть хранится в весах | прогноз корректен, даже если backend передаёт сеть с уже внесёнными правками |
| Нет изменений → база без вызова модели | карта «до» совпадает с базой в точности, сравнение «до/после» без ложных изменений |
| Разбиение по сценариям | нет утечки одного сценария между обучением и тестом |
| Макромодель BPR + MSA для синтетики | быстро (≈0,2 с на сценарий), но воспроизводит объезды и заторы — то, ради чего нужна GNN |
| Заглушки в `ml/data/` | правило «работать только в своей папке»; формат совпадает с ожидаемым от `sim/` |
| Только CPU | прототип для одного района; инференс — миллисекунды и без GPU |

## Ограничения и дальнейшая работа

* **Веса обучены на пилотном датасете SUMO** (300 сценариев, 210 — обучение).
  Этого мало: кривые обучения расходятся (переобучение), а эффект изменений
  сравним с шумом симуляции. Для полноценной модели нужен датасет из тысяч
  сценариев и повторение абляции на нём — см. «Что осталось сделать» в
  корневом README.md. Сравнение архитектур (разделы «Результаты» выше)
  выполнено на синтетике.
* Изменение `traffic_light` моделируется бинарно (есть/нет светофора);
  режимы управления (фиксированный / адаптивный / RL-агент из `agents/`)
  могут стать дополнительным признаком узла, когда `sim/` начнёт их варьировать.
* Модель предсказывает «среднее» состояние за период симуляции, без
  динамики по времени суток; естественное развитие — добавить время суток
  или уровень спроса как признак.
* Оценка неопределённости прогноза (например, ансамбль или MC-dropout)
  помогла бы показывать пользователю доверительный интервал.
